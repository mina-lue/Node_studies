QUESTION 7 — The I/O scaling problem (7 points)

Explain the I/O scaling problem and compare these three server designs:

    one process per request
    one thread from a pool per request
    Node.js event-loop-based request handling

Discuss CPU use, memory use, waiting for I/O, and context-switching overhead.
Conclude by explaining why JavaScript's first-class functions and closures make
it suitable for Node.js's approach.

ANSWER:


I/O scaling problem is challenge on servers to handle thousands of I/O requests simultaneously. Some of the I/O requests include database queries, network calls and disk file content operations. IF I/O approach used is blocking meaning if the process or thread has to wait till the IO operation ends we will have our CPU and memory resources wasted because of overhead more than the actual work.

The three server designs
1. One process per request
  a. CPU and context switching: high overhead as the number of requests grow in number, we will have lot of processes to manage. 
  b. Memory usage: Memory consumption is considerably high as processes use their own memory spaces each.
  c. waiting I/O: Every IO requests will be blocking the process up to the operations finishes up.

1. One thread from a pool per request
  a. CPU and context switching: Moderate in relative to One process per request design but still consumes a lot of cpu resources and needs tracking multiple threads. high overhead still.
  b. Memory usage: better memory usage in relative to one process per request as threads share memory, but still increases memory consumption as requests grow. 
  c. waiting I/O: blocking, if we have no more threads in pool the request will have to wait even with no thread named for it.

1. Node.js event-loop-based handling
  a. CPU and context switching - single threaded, small overhead as result of single execution thread.
  b. Memory usage - memory usage is optimal as we have single thread in the app, almost predictable 
  c. waiting I/O - no request blocking as every IO requests gets delegated to OS kernel by libuv so our execution thread is always ready to accept other requests.


# Node.js relies on asynchronous, event driven pattern: when an asynchronous operation is initialized, the program passes callback function to handle the response later. To make this feature viable we need First class functions and closures.
First class functions - allows passing functions as argument.
Closures - hold the surrounding lexical state and variables at the exact moment the asynchronous call was made. Since the callback functions are executed long after the outer function has returned, closures keep the context for the callback.

QUESTION 10 — Filesystem APIs and asynchronous errors (4 points)

Compare synchronous and asynchronous fs operations in a busy server. Explain
why a try/catch surrounding the call that schedules an asynchronous operation
does not catch an error later thrown by its callback. State the Node.js
error-first callback convention for both failure and success.

ANSWER:

# Synchronous fs operations block the main thread while waiting for slow IO (disk) operation to complete. In busy server this would entirely stop event loop from accepting any new requests. Asynchronous fs offloads the disk IO to libuv worker threads and leaves event loop to handle other requests.

# Try catch finishes executing before the async operations get executed. The async operation schedules the IO task and immediately finishes, the try/catch gets executed and gets removed from call stack, long after try/catch the disk operations finishes and places its callback into event queue,  when the event loop later executes the callback there is no active try/catch.

# here is how error first call back convention for both failure and success; every callback is passed error as first argument and data as second, so in order to find out if error has occurred we check if the first argument is null or undefined. If first argument is null or undefined it means the operation was successful!

QUESTION 12 — Closure and asynchronous callbacks (5 points)

What is printed, and why?

    function makeReporter(label) {
        var count = 0;
        return function () {
            count = count + 1;
            console.log(label + ':' + count);
        };
    }

    var alpha = makeReporter('A');
    var beta = makeReporter('B');

    setTimeout(alpha, 0);
    alpha();
    beta();
    setTimeout(beta, 0);
    console.log('scheduled');

ANSWER:

A:1
B:1
scheduled
A:2
B:2

-> Explanation:

Independent Closures:
Calling makeReporter('A') and makeReporter('B') creates two separate closure instances in memory. Each returned function retains access to its own distinct count variable within its lexical environment. As a result, alpha and beta increment their own separate counters independently.

Synchronous vs. Asynchronous Execution Order:

All synchronous code executes first on the call stack before any timer callbacks can run:

alpha() increments alpha's count to 1 and logs A:1.

beta() increments beta's count to 1 and logs B:1.

console.log('scheduled') logs scheduled.

Even though setTimeout(..., 0) specifies a delay of 0 ms, its callback is placed into the event loop's timers queue. The event loop can only process queued callbacks once the synchronous call stack is completely empty.

Once the main thread finishes executing the synchronous code, the event loop runs the queued callbacks in order:

The queued alpha callback increments alpha's counter to 2 and logs A:2.

The queued beta callback increments beta's counter to 2 and logs B:2.
